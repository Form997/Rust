## 1. Purpose and scope

H0.1 expands the initial architecture review. AL must not be designed as only a lexer/parser plus one LLM. The review covers the foundations needed for a reliable language and local intelligence system:

1. data representation and data structures;
2. algorithms, complexity, numerical computing, and optimization;
3. mathematics and scientific computing;
4. physical sciences and other extensible knowledge domains;
5. machine learning and learning algorithms;
6. local LLM/LLMs, inference, retrieval, and model management;
7. local hardware constraints, privacy, safety, and evaluation;
8. the interface between natural-language intent, AL source, deterministic validation, and execution.

This document is a design and investigation plan. Listing a technique does not mean it has been implemented, selected, or proven suitable.

## 2. Non-negotiable architecture principles

- **One AL language authority:** grammar, AST, types, semantics, and execution rules come from the versioned AL specification and Rust implementation.
- **Multiple specialized engines:** deterministic algorithms, scientific solvers, retrieval, and learned models are separate components with explicit contracts.
- **AI is not a source of truth:** generated statements and programs must carry provenance or uncertainty where appropriate and pass deterministic validation.
- **Local-first:** useful core functions must remain available without internet access.
- **Hardware-aware:** the system must degrade gracefully from workstation to CPU-only low-memory devices.
- **No forced LLM dependency:** AL parsing, type checking, numerical algorithms, and safe execution must work without an LLM.
- **Evidence before adoption:** every major algorithm or model choice needs benchmark data, resource measurements, license review, and tests.
- **Extensible scientific domains:** physics, chemistry, biology, agriculture, engineering, and other domains are pluggable knowledge/solver packages, not hard-coded assumptions in the language core.

## 3. Data architecture and data structures

H0.1 must inventory data shapes, access patterns, mutability, memory use, persistence, and worst-case behavior before choosing structures.

### 3.1 Core structures to evaluate

| Structure | Appropriate uses | Review questions |
|---|---|---|
| Contiguous arrays / vectors | Tokens, source bytes, AST child lists, numeric sequences | Allocation, locality, resize cost |
| Strings and ropes/piece tables | Source text and editor changes | Unicode, slicing, incremental edits |
| Hash maps / sets | Symbol tables, registries, caches | Determinism, collision behavior, memory |
| Ordered maps / B-trees | Stable ordered indexes and ranges | Range query and persistence needs |
| Trees | AST, type structures, syntax hierarchy | Ownership, traversal, recursion limits |
| Graphs | Dependencies, dataflow, knowledge relations | Cycles, traversal, graph size |
| Tries / finite-state automata | Keywords, completion, lexical patterns | Unicode and incremental lookup |
| Heaps / priority queues | Scheduling and search | Stable ordering and complexity |
| Sparse matrices / sparse vectors | Scientific models and high-dimensional features | Density threshold and storage format |
| Dense tensors | Neural-network and numerical workloads | Shape safety, precision, memory |
| Columnar tables | Datasets and analytical workloads | Scan speed, schema evolution |
| Append-only logs | Audit, training lineage, reproducibility | Integrity, retention, compaction |
| Disk-backed indexes | Large local corpora | Recovery, corruption, bounded RAM |

No structure should be selected merely because it is familiar. The implementation must state invariants, ownership rules, expected complexity, serialization format, and failure behavior.

### 3.2 Data contracts

Define versioned schemas for at least:

- source files, source spans, tokens, AST nodes, diagnostics;
- symbols, types, modules, dependencies, and build artifacts;
- scientific quantities, units, dimensions, uncertainty, and provenance;
- training examples, labels, splits, datasets, and transformations;
- model metadata, tokenizer metadata, prompts/templates, and evaluation records;
- retrieval documents, chunks, embeddings, indexes, and citations;
- tool capabilities, execution requests, resource limits, and audit events.

All externally loaded data is untrusted. Schemas require size limits, validation, explicit versions, and safe failure behavior.

### 3.3 Unicode and language data

- Preserve source text and source offsets consistently.
- Define UTF-8 handling and Unicode normalization policy explicitly.
- Do not assume Vietnamese text is ASCII or that one normalization form is always interchangeable.
- Test combining marks, tone marks, emoji, mixed scripts, regional language, and invalid byte sequences.
- Keep source byte offsets and user-visible character positions clearly distinguished.

## 4. Algorithm foundations

H0.1 must create a catalogue of algorithms by workload, with correctness conditions and complexity.

### 4.1 Language and compiler algorithms

- lexical scanning and finite-state machines;
- recursive-descent, Pratt, or other parser strategies after grammar review;
- symbol-table construction and scope resolution;
- type inference/checking where specified;
- graph algorithms for module dependencies and cycle detection;
- dataflow analysis and intermediate-representation passes;
- incremental parsing and caching only when justified by editor/workload measurements.

### 4.2 General algorithm families

- sorting, searching, hashing, indexing;
- graph traversal and shortest-path algorithms where relevant;
- dynamic programming and greedy methods;
- constraint solving and optimization;
- streaming algorithms and approximate summaries;
- parallel and concurrent algorithms;
- numerical integration, root finding, linear algebra, and differential-equation solvers.

Each algorithm record must include: problem definition, assumptions, correctness argument or reference, time complexity, space complexity, numerical stability if applicable, adversarial cases, test corpus, and benchmark.

### 4.3 Complexity and resource governance

- Define limits for source size, nesting depth, AST node count, execution steps, memory, recursion, and wall-clock time.
- Prefer predictable algorithms for untrusted input.
- Include denial-of-service tests and worst-case benchmarks.
- Avoid claiming an algorithm is scalable without measuring representative and adversarial inputs.

## 5. Mathematics and scientific computing

The platform should distinguish exact symbolic work from floating-point numerical work.

### 5.1 Foundations to assess

- arithmetic, algebra, functions, logic, sets, relations, and proof-oriented reasoning;
- calculus, differential and integral equations;
- linear algebra, matrices, eigenvalues, decompositions;
- probability, statistics, estimation, and uncertainty;
- discrete mathematics, combinatorics, and graph theory;
- numerical analysis, error propagation, conditioning, and stability;
- optimization, including constrained and multi-objective methods;
- dimensional analysis and unit conversion.

### 5.2 Numerical correctness

Scientific values should carry units/dimensions where the domain requires them. The system must distinguish:

- integer, rational, decimal, and binary floating-point representations;
- exact values from approximations;
- measured values from calculated estimates;
- input uncertainty from numerical error;
- a solver result from a verified scientific conclusion.

Tests must include reference solutions, boundary cases, convergence checks, sensitivity tests, and tolerances justified by the problem. Do not silently mix incompatible units.

## 6. Physical sciences and domain knowledge

The phrase “scientific knowledge” is broader than physics. H0.1 should establish a domain-package model rather than attempting to encode all sciences in the AL core.

Initial domain families to review:

- **Physics:** mechanics, thermodynamics, electromagnetism, waves, optics, fluid mechanics, and relevant modern-physics topics.
- **Chemistry:** composition, reactions, equilibrium, kinetics, and thermochemistry.
- **Biology:** systems, genetics, physiology, ecology, and biological processes.
- **Earth and environmental sciences:** soil, water, climate, hydrology, and environmental processes.
- **Agriculture:** crop systems, soil fertility, plant nutrition, irrigation, pests, and production systems.
- **Engineering:** materials, structures, control, energy, and process systems.

Each domain package must declare its scope, concepts, equations, units, assumptions, parameter sources, validity ranges, uncertainty, and test references. Domain packages must not present a model's plausible text as experimental evidence.

A scientific solver should expose structured inputs and outputs. The LLM may help translate a question into a candidate structured problem, but a validated solver performs the calculation.

## 7. Learning algorithms and machine learning

The selected project direction is AL-owned model weights trained from scratch. This is not a claim that a large foundation model can be trained on the currently available personal computer. Begin with measurable, small tasks.

### 7.1 Learning paradigms to evaluate

- rule-based systems and symbolic methods as deterministic baselines;
- supervised learning for classification and structured prediction;
- unsupervised learning for clustering and representation exploration;
- self-supervised learning for language and sequence representations;
- retrieval-based learning and ranking;
- reinforcement learning only where a safe environment, reward definition, and evaluation method exist;
- hybrid neuro-symbolic methods combining learned suggestions with deterministic constraints.

### 7.2 Model families to investigate

- linear/logistic models and naive Bayes;
- decision trees and ensembles;
- nearest-neighbor and ranking methods;
- compact neural networks and sequence models;
- transformer-based language models;
- embedding models for semantic retrieval;
- rerankers and small task-specific models.

For each candidate, record task fit, data requirements, compute, RAM, latency, interpretability, failure modes, licensing, and held-out evaluation. Do not select a model architecture by trend alone.

### 7.3 Training discipline

- Maintain train/validation/test separation.
- Prevent duplicate and near-duplicate leakage across splits.
- Record dataset lineage and rights review.
- Fix and record seeds where applicable.
- Save configurations, checkpoints, metrics, and checksums.
- Compare against deterministic and simple statistical baselines.
- Track hallucination, abstention, calibration, and out-of-distribution behavior.
- Do not call a model “trained” or “accurate” without reproducible evidence.

## 8. Local LLM / LLMs architecture

“LLM” refers to a large language model; “LLMs” is the plural. AL should support a model-independent interface rather than bind its architecture to one vendor or one model family.

### 8.1 Separate the local AI capabilities

1. **Intent router:** determines whether a request needs rules, retrieval, a scientific solver, a language tool, or an LLM.
2. **Local LLM runtime adapter:** loads and runs a supported local model.
3. **Tokenizer adapter:** records model-specific tokenization and special-token behavior.
4. **Embedding model:** maps text to vectors for semantic retrieval.
5. **Retrieval engine:** searches approved local documents and returns source references.
6. **Reranker:** optionally reorders retrieval candidates.
7. **AL generation adapter:** proposes AL source or structured actions.
8. **Validation client:** submits candidate AL to Rust and returns diagnostics.
9. **Model registry:** records model identity, format, license, checksum, quantization, hardware profile, and approved purpose.

These components may share a process initially, but their interfaces and responsibilities must remain separate.

### 8.2 Local inference techniques to evaluate

- CPU inference and hardware acceleration where available;
- quantization (for example, lower-bit weight formats) with measured quality loss;
- memory mapping and lazy loading;
- context-window limits and prompt budgeting;
- batching only where it improves measured throughput;
- streaming output and cancellation;
- model caching and eviction;
- deterministic decoding settings for repeatable tasks;
- model adapters and format conversion with integrity checks.

Potential runtimes and formats are candidates for investigation, not pre-approved dependencies. Every option requires compatibility, security, license, memory, latency, and quality testing.

### 8.3 Retrieval-augmented generation (RAG)

RAG is a retrieval workflow, not a guarantee of truth. H0.1 should compare:

- lexical search such as BM25;
- vector search over local embeddings;
- hybrid lexical + vector retrieval;
- reranking;
- chunking strategies and metadata filters;
- citation and source-span preservation;
- freshness, deletion, and index rebuild behavior.

A response that cannot find adequate evidence should say so. Retrieved content is data, never executable instruction. Every cited answer should identify its source and distinguish quotation, summary, inference, and unknowns.

### 8.4 Local model profile for constrained devices

The known baseline device for initial feasibility testing is a CPU-only computer with approximately 4 GB RAM. This is a severe constraint.

Required design behavior:

- AL lexer/parser/type-checker and core CLI operate without any LLM.
- A rule-based intent layer provides a useful fallback.
- Embeddings and LLMs are optional modules.
- A model must not load automatically if the estimated memory budget is unsafe.
- Measure peak resident memory, startup time, tokens/second, first-token latency, disk footprint, and task quality.
- Prefer small, quantized, task-specific models when evidence supports them.
- Training a general-purpose LLM on this machine is out of scope.
- Larger training runs may use stronger local or rented compute, with reproducible manifests and controlled artifact transfer.

Do not promise that any named model fits until tested on the target operating system and hardware.

## 9. Integration with AL execution

The safe workflow is:

1. Parse the user's request into a typed intent proposal.
2. Decide which deterministic tool, retrieval source, scientific solver, or LLM is appropriate.
3. Produce structured parameters or candidate AL source.
4. Validate schema and provenance.
5. Run the candidate through the Rust lexer/parser/semantic/type pipeline.
6. Show diagnostics and request clarification if intent or evidence is insufficient.
7. Request explicit permission for any execution or external capability.
8. Execute only through the sandbox and enforce resource limits.
9. Return outputs with input parameters, tool/model versions, sources, and uncertainty.

The LLM must never modify compiler rules, grant its own permissions, or bypass the Rust validator.

## 10. H0.1 investigation deliverables

H0.1 is complete only when the repository contains reviewed, versioned deliverables:

- data-structure catalogue with workload mapping;
- data contracts and serialization policy;
- algorithm catalogue with complexity and test strategy;
- mathematics/numerical computing decision record;
- scientific domain-package interface;
- machine-learning method comparison;
- local LLM/LLMs runtime and model-format comparison;
- RAG and local-index design;
- hardware feasibility benchmark plan;
- privacy, security, licensing, and provenance review;
- architecture decision records (ADRs) for selected and rejected options;
- explicit implementation backlog for H1 onward.

## 11. Exit criteria

H0.1 is not complete merely because this document exists. Exit requires:

1. Existing AL 0.1 source, specification, tests, and repository history reviewed.
2. Data structures mapped to actual AL workloads.
3. Language-core algorithms separated from optional AI/science modules.
4. Local model feasibility evaluated against declared hardware profiles.
5. At least one deterministic baseline defined for each AI-assisted task.
6. All proposed dependencies checked for license, maintenance, platform, and security.
7. Open questions and rejected alternatives documented.
8. A prioritized H1 implementation plan approved without silently changing the AL 0.1 grammar.

## 12. Open questions requiring evidence

- Which scientific quantities and units need first-class type support, and which belong in domain libraries?
- Should AL use a built-in tensor type, a standard library, or external numerical packages?
- What is the minimal portable model interface across CPU runtimes?
- What are the actual Lite RAM and latency targets?
- Which tokenizer and model formats can be distributed under acceptable terms?
- Which local retrieval index best balances disk, RAM, quality, and rebuildability?
- Which learning tasks are sufficiently narrow to justify training a small AL-owned model first?
- What scientific reference datasets and benchmarks are lawful, reliable, and reproducible?

## 13. Status boundary

This H0.1 document defines the investigation scope and exit evidence. It does not assert that the listed data structures, algorithms, scientific solvers, LLM runtimes, RAG components, or learning models have been implemented or benchmarked.
