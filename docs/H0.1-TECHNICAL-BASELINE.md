# H0.1 Technical Baseline — Data, Algorithms, Scientific Computing and Local AI

- Document ID: AL-H01-TECH-BASELINE-001
- Version: 1.0.0
- Status: Design baseline approved for H1 planning; implementation and benchmarks remain pending
- Date: 2026-11-27
- Normative language: MUST = required; SHOULD = recommended; MAY = optional

## 1. Decision summary

This document converts the H0.1 review into an implementable baseline without changing AL 0.1 grammar or claiming planned subsystems already exist.

| Area | H0.1 decision | Reason / boundary |
|---|---|---|
| Language authority | Rust owns lexer, parser, AST, semantic checks, AL-IR validation and execution policy | AI output is untrusted |
| Core collections | Start with Rust Vec, String, HashMap/HashSet; BTreeMap for ordered/range queries | Low dependency and memory overhead |
| Source positions | Canonical spans are UTF-8 byte offsets; SourceMap derives line/column | Exact slicing; UI columns are Unicode-aware |
| Syntax representation | Typed AST nodes with spans | Avoid untyped generic JSON as compiler internals |
| Persistence | Versioned UTF-8 JSON for interchange; SQLite is an optional index candidate | Portable and local-first |
| Scientific quantities | Value + unit/dimension + uncertainty + provenance | Prevent invalid scientific arithmetic |
| Numerical work | Exact representations where needed; f64 baseline for ordinary numerical solvers with explicit tolerances | Make approximation visible |
| Domain sciences | Pluggable domain packages | Keep science out of language-core assumptions |
| ML strategy | Deterministic baseline first; small task-specific models second; general LLM last | Measurable gains and realistic compute |
| Local inference | Runtime adapter; benchmark llama.cpp/GGUF and ONNX Runtime by role | No production runtime before target-device tests |
| RAG | Lexical retrieval first; optional embeddings/reranking; citations preserve source spans | Low-memory fallback and traceability |
| Lite mode | AL core works without AI; optional model obeys explicit RAM budget | Target is CPU-only ~4 GB RAM |
| Execution | Deny by default; capability-scoped sandbox; explicit approval for effects | AI cannot grant permissions |

## 2. Workload-to-data-structure catalogue

| Workload | Initial structure | Required invariant | Complexity / note |
|---|---|---|---|
| Source buffer | UTF-8 String / byte slice | Immutable snapshot while lexing; valid UTF-8 | O(1) byte slicing |
| Tokens | Vec<Token> | Source order; spans monotonic and in bounds | O(n) scan/storage |
| AST child lists | Vec<NodeId> or owned Vec<Node> | Ownership is acyclic unless explicit graph IR | O(1) append |
| Symbol scopes | HashMap<Name, SymbolId> per scope | Duplicate and shadowing rules explicit | Expected O(1) lookup per scope |
| Deterministic output | BTreeMap or sorted Vec | Stable serialized order | O(log n) update or O(n log n) sort |
| Module dependencies | Adjacency lists + DFS/Kahn | Cycle reports include path | O(V+E) |
| Diagnostics | Vec<Diagnostic> | Stable code, span, severity, related spans | O(1) append |
| Numeric vectors | Vec<f64> initially | Shape/unit metadata checked separately | O(n) operations |
| Sparse matrices | CSR/CSC candidate | Sorted indices; canonical duplicate handling | O(nnz) storage |
| Scientific tables | Columnar arrays + schema | Equal column lengths; explicit missing-value policy | Contiguous scans |
| Local document index | SQLite FTS5 candidate | Source id/version/span/deletion state retained | Inverted-index retrieval |
| Embeddings | Flat f32/f16 arrays + metadata | Fixed dimension, model id, normalization policy | Exact scan baseline first |
| Audit/training history | Append-only records | Hash, timestamp, actor/source, schema version | Append-first |

### 2.1 Memory and ownership policy

- Keep source spans, token metadata and AST nodes compact; do not copy source substrings into every token.
- Adopt arena/ID-based AST allocation only after profiling demonstrates allocation pressure.
- Use bounded caches with explicit eviction; no unbounded global cache.
- Large tensors and datasets are streamed/chunked in Lite mode.
- External inputs have maximum byte size, nesting depth, record count and parse budget.
- Sort map keys where deterministic serialization matters.

## 3. Versioned data contracts

The machine-readable starting schemas are in schemas/h0-1-data-contracts.schema.json. They cover source documents, spans, tokens, diagnostics, scientific quantities, provenance, model manifests, training records, retrieval chunks, capability requests and execution requests.

Contract rules:
1. Every persisted/inter-process record MUST carry schema_version.
2. Unknown major schema versions MUST fail closed.
3. Numeric fields MUST declare unit and precision semantics where applicable.
4. Every model artifact MUST carry checksum and source/license metadata.
5. Every retrieval chunk MUST retain document id, version, source span and access classification.
6. Every execution request MUST be capability-scoped and resource-bounded.
7. JSON Lines bridge messages MUST be one complete JSON object per line; stdout is protocol-only and logs go to stderr.
8. Reject oversized payloads, invalid UTF-8, unknown enum values and duplicate identifiers.

## 4. Algorithm catalogue and acceptance conditions

| Subsystem | Candidate algorithm | Correctness / failure condition | H1 test requirement |
|---|---|---|---|
| Lexer | Single-pass deterministic scanner | Token spans ordered, in-bounds and traceable | Golden tests, malformed Unicode/escape cases, fuzzing |
| Parser | Recursive descent for declarations; Pratt for expressions if adopted | Grammar ambiguity and recovery explicitly specified | Valid/invalid corpus; bounded nesting |
| Scope resolution | Scope stack + symbol maps | Duplicate/undefined names diagnosed | Nested scope, shadowing, duplicate tests |
| Type checking | Syntax-directed or constraint-based after type rules freeze | No unsafe implicit coercion | Positive/negative type matrix |
| Module graph | Kahn sort + DFS cycle path | Cyclic imports rejected with actionable path | DAG, self-cycle, multi-node cycle |
| IR validation | Typed IR verifier | Invalid control flow/type/capability rejected | Mutation and fuzz tests |
| Search | BM25/FTS5 baseline; vector search optional | Recall measured; spans retained | Recall@k, MRR/nDCG, latency |
| Ranking | Linear ranking baseline; reranker optional | No relevance claim without labelled test set | nDCG@k, MRR, calibration |
| Numeric solving | Stable algorithm selected per problem class | Residual, convergence, conditioning reported | Reference solutions/tolerance tests |
| ODE/PDE | Solver chosen by equation class | Stability, boundary conditions documented | Convergence order, conservation checks |
| ML classification | Majority/linear/logistic/naive Bayes baseline | Leakage-free split | Macro-F1, per-class recall, calibration |
| Intent routing | Rules first; classifier only if rules are outperformed | Uncertain requests abstain | Confusion matrix, false-action rate |
| Generation | Structured output + Rust validation | Invalid output cannot reach execution | Schema/compile pass rates, refusal tests |

No universal algorithm is mandated where numerical or semantic properties differ by workload.

## 5. Mathematics and scientific computing baseline

### 5.1 Mathematical capability layers

- Foundations: arithmetic, logic, sets, relations, functions, algebra and discrete mathematics.
- Calculus: limits, differentiation, integration and differential equations.
- Linear algebra: vector spaces, matrices, rank, eigenvalues, decompositions and sparse systems.
- Probability/statistics: distributions, estimation, tests, regression, uncertainty and experimental design.
- Numerical analysis: floating-point representation, cancellation, conditioning, stability, convergence and error propagation.
- Optimization: unconstrained/constrained, linear/nonlinear, integer and multi-objective methods.
- Dimensional analysis: unit algebra, conversion, dimensional consistency and significant figures.

### 5.2 Numeric type policy

| Representation | Use | Caution |
|---|---|---|
| Integer | Counts, indices, exact discrete quantities | Not for valid fractional values |
| Rational | Exact ratios and symbolic transformations | Denominator growth |
| Decimal | Human-entered decimal/business values | Not ideal for high-throughput linear algebra |
| f32/f64 | Simulation, statistics and ML tensors | Not exact decimal arithmetic |
| Interval/uncertainty wrapper | Bounded measurement ranges | Not a probability distribution unless defined |

No implicit conversion across incompatible dimensions. Every solver declares units, domain, tolerances and convergence status. Distinguish measurement, parameter, model and numerical uncertainty. Report residuals; numerical output is not scientific proof. Reference data must identify source, version, units, conditions and license.

### 5.3 Domain-package contract

A scientific domain package declares:
- package id, semantic version, domain and subdomain;
- glossary and concept identifiers;
- equations/algorithms with source references;
- quantity/unit definitions and conversion rules;
- parameter tables with provenance and validity ranges;
- solver input/output schemas;
- assumptions, boundary/initial conditions and limitations;
- uncertainty and sensitivity method;
- reference datasets and reproducible tests;
- package license and maintainer.

Initial domains: physics, chemistry, biology, earth/environment, agriculture and engineering. Domain packages are optional libraries and do not silently alter AL core semantics.

## 6. Machine-learning method selection

| Task | Baseline | Candidate learned method | First evaluation |
|---|---|---|---|
| Intent classification | Hand-authored rules | Logistic regression / small text classifier | Macro-F1, false route rate, abstention |
| Document retrieval | BM25 | Embedding + hybrid ranker | Recall@k, MRR, nDCG |
| Semantic similarity | TF-IDF/cosine | Small embedding model trained from scratch | Correlation on held-out pairs |
| Field extraction | Deterministic parser/regex | Sequence tagger or compact transformer | Exact match, field F1 |
| AL code suggestion | Templates/examples | Small code/text model | Parse, semantic and task pass rates |
| Scientific prediction | Domain baseline/regression | Tree ensemble or neural net | MAE/RMSE, calibration, external validation |
| Anomaly detection | Threshold/statistical control | Isolation forest/autoencoder if justified | Precision-recall, false alarm rate |

Training protocol:
1. Write a task card with users, inputs/outputs, prohibited actions and failure costs.
2. Create lawful data with documented consent/license and provenance.
3. Split by source/entity/time where leakage is plausible; deduplicate before splitting.
4. Freeze the test set and keep it inaccessible during tuning.
5. Compare deterministic, statistical and learned baselines.
6. Record seed, code revision, dependencies, hardware, hyperparameters and data hashes.
7. Report per-class metrics, calibration, abstention and domain error.
8. Release weights only after governance, reproducibility and security review.

First model recommendation: do not begin with a general chatbot. Evaluate a small intent classifier or AL-specific structured extraction task with labelled data. Approval requires measured improvement over rules.

## 7. Local LLM and runtime decision

### 7.1 Runtime roles

| Candidate | Appropriate role | H0.1 position |
|---|---|---|
| llama.cpp + GGUF | CPU-oriented local text generation and quantized inference | First runtime to benchmark for local LLM feasibility |
| ONNX Runtime | Portable inference for task encoders/classifiers/embedders | Candidate for compact non-generative models |
| Hugging Face Transformers | Python model research, training/evaluation and quantization workflows | Development ecosystem; not default 4 GB runtime |
| Native Rust deterministic components | Lexer/parser/validator/router rules | Mandatory baseline, independent of LLM |

This is a shortlist, not endorsement of a specific model, binary, checkpoint or license.

### 7.2 LLM acceptance gates

A model is accepted only if its model card/license are reviewed; tokenizer/template/context are pinned; checksum and quantization verified; peak memory includes weights, KV cache, runtime, prompt and OS headroom; target-device latency and quality measured; structured-output failures and prompt injection tested; and AL remains usable with the model disabled.

Weight size is not total runtime memory. Quantization may reduce weight storage but does not remove KV cache, activations, runtime overhead or OS memory. Never promise fit based only on parameter count.

## 8. RAG and local knowledge store

### 8.1 Staged design

- Stage A: source registry + lexical index (BM25/FTS5 candidate).
- Stage B: optional local embedding model and vector index.
- Stage C: hybrid candidate fusion and optional reranker.
- Stage D: evidence assembly with exact source spans, document version, timestamps and access rights.

### 8.2 Required retrieval metadata

Each document/chunk stores stable document id and immutable version/hash; source URI/path and title; publication/retrieval timestamps where known; license/access class/deletion state; chunk id and byte/page/section span; language and tokenizer/index version; embedding model id and dimension if embedded.

### 8.3 Retrieval safety

Retrieved text is data, never instructions to model/runtime. Apply access control before ranking and returning snippets. Deletion invalidates chunks, embeddings and cached answers. Citations resolve to a specific source version/span. Low or conflicting evidence produces abstention or qualification. Measure retrieval separately from generation.

## 9. Hardware profiles and benchmark plan

| Profile | Target | Enabled behavior |
|---|---|---|
| Lite | CPU-only, 4 GB RAM | AL core, rules, lexical retrieval, small files; no auto-loaded LLM |
| Standard | 8–16 GB RAM, modern CPU/modest accelerator | Optional small quantized model after benchmark |
| Development | 16–32+ GB RAM and/or GPU | Dataset preparation, experiments, small-model fine-tuning/evaluation |
| Training | Strong local or rented compute | Larger runs with provenance, budget and artifact controls |

These are planning bands, not guarantees.

Every benchmark records CPU/core count, RAM, OS, storage/free disk, toolchain/runtime versions, model/tokenizer hashes, quantization/context, dataset hash, cold/warm startup, peak RSS, disk footprint, first-token latency, median/p95 latency, tokens/sec, quality, abstention and reproducibility.

Test idle CLI and lexer; parser when implemented; lexical retrieval; embedding independently; LLM cold start/short and long prompts/cancellation; concurrent load; offline startup; corrupted/missing model; insufficient-memory behavior.

Lite acceptance: AL core passes conformance tests with AI absent; LLM is opt-in and cannot load if memory headroom is unsafe; budgets are measured; model failure falls back without corrupting user data. The 4 GB PC is a feasibility target, not a promise of useful general LLM performance.

## 10. Security, privacy and governance gates

- Deny by default for filesystem, network, process and device access.
- Capability request and grant are separate; only trusted policy/user action grants.
- Validate AI-generated AL through Rust; never execute raw model output.
- Check source/model/retrieval provenance.
- Keep secrets out of datasets, prompts, logs and fixtures.
- Apply data minimization, retention/deletion and encryption where warranted.
- Verify model artifact origin/checksum; scan and pin dependencies; review licenses.
- Record incidents, roll back affected artifacts and publish corrections.

## 11. H0.1 decisions and unresolved items

Decisions: Rust is sole language/security authority; Python is model research/training/evaluation; JSON Lines is initial bridge; deterministic baselines precede learned components; LLM optional; FTS5/BM25 is lexical retrieval candidate; scientific domains are modular; Lite works without LLM; H0.1 does not change grammar.

Pending evidence: first-class unit/tensor/uncertainty type semantics; first AL-owned model task; actual model RAM/latency; final runtime/vector-index choice; lawful dataset inventory; Rust/Python solver placement by workload.
