# H0.2.6 — Rulebook Enforcement Core

**Status:** Implemented on the H0.2.6 development branch; requires review and explicit merge.  
**Parent:** H0.2.5 Root of Trust and Rulebook Update Center.

## Purpose

H0.2.6 turns an approved, human-signed Rulebook into a fail-closed authorization decision for AL subsystem gates. It does not allow AI-generated content, an unsigned policy, an unapproved rule, or missing policy data to authorize an operation.

## Governed gates

The first enforcement contract defines seven stable gate identifiers:

- `compiler`
- `runtime`
- `ai`
- `training`
- `evaluation`
- `scientific`
- `release`

A gate is permitted only when all of these conditions hold:

1. The trust registry has already been verified against the out-of-band root fingerprint.
2. The Rulebook envelope is signed by an active key with the `rulebook_authority` role.
3. The signed payload status and its approval record are `approved`.
4. The approval principal matches the trusted signer principal.
5. At least one rule has `status: approved`, includes the exact gate identifier in `scope`, and contains one or more non-empty `control_ids`.
6. The gate identifier is one of the seven explicitly supported identifiers.

Missing files, malformed data, missing rules, unknown gates, missing controls, invalid signatures, revoked signers, and unapproved rules all deny authorization. There is no permissive fallback.

## Rule representation

Example fragment inside a signed Rulebook payload:

```json
{
  "rule_id": "AL-SEC-COMPILER-001",
  "status": "approved",
  "title": "Compiler operations require approved policy controls",
  "scope": ["compiler"],
  "control_ids": ["CTRL-COMPILER-POLICY-001"]
}
```

The control identifier must resolve to a documented, testable control in the full Rulebook control catalogue. H0.2.6 currently checks that the identifier is present and non-empty; it does not yet resolve controls to implementation evidence or prove that a future compiler/runtime/AI module has wired the gate correctly.

## CLI

```sh
cargo run -- rulebook gate compiler \
  approved-rulebook-envelope.json \
  root-signed-trust-registry.json \
  <64-hex-root-fingerprint>
```

Supported gate values: `compiler`, `runtime`, `ai`, `training`, `evaluation`, `scientific`, `release`.

A successful response is an authorization permit containing the gate, Rulebook version and matching rule IDs. A non-zero exit code means denied. The command is a policy preflight; it does not itself compile, execute, train, evaluate or release anything.

## Integration contract for future modules

Each governed subsystem must call the same Rust authorization API before starting a protected operation, then bind the returned permit to the operation context. It must not accept a Boolean or permit supplied by an AI model, client request, or unsigned configuration. Recheck authorization at security boundaries and before long-running jobs commit outputs. No module may cache an authorization decision across Rulebook changes without pinning the exact verified bundle hash and applying a documented freshness/revocation policy.

|---|---|---|
| Compiler | Implemented | Pending; parser/compiler not yet implemented |
| Runtime | Implemented | Pending; runtime not yet implemented |

Do not describe these future modules as already protected. H0.2.6 provides the central gate and integration contract; later phases must wire each real subsystem and add integration tests.

## Tests

Unit tests cover all seven positive gates and fail-closed cases for absent rules, proposed rules, missing control IDs, and unknown gate names. CI also runs the complete Rust test suite and verifies that an untrusted root registry cannot pass the CLI gate.

## Security and operational limits

- The root fingerprint must be supplied by deployment configuration protected separately from the registry and repository checkout.
- No production private keys are stored in this repository.
- The gate verifies signature, approval identity and declared policy controls; it does not independently prove legal compliance, source authenticity, scientific correctness, or control effectiveness.
- The current signature serialization uses the existing serde_json serialization convention. A formally specified canonical JSON format remains a hardening task before interoperability with independent signers.
- Human identity is represented by a trusted key principal ID. Production identity proof, key custody, recovery and protected-host administration remain deployment responsibilities.
- A compromised host, executable, or root-pin configuration can defeat local enforcement. Production deployment needs an independently protected root of trust and security review.
