# H0.2.5 — Root of Trust and Rulebook Update Center

**Status:** Implementation proposal; requires independent security review and deployment configuration.  
**Branch:** `h0-2-5-root-of-trust-update-center`

## Goals

H0.2.5 closes the H0.2.4 trust-registry substitution gap and adds a command-line update review workflow. It does not silently activate a policy or create a production signing identity.

## Trust chain

1. An offline root authority signs a trust-registry payload using Ed25519.
2. The verifier checks the root public-key SHA-256 fingerprint against a pin supplied from separately protected deployment configuration.
3. The verifier validates the root signature and validates registry structure, key IDs, roles, statuses and public keys.
4. A Rulebook maintainer key in that verified registry signs the candidate Rulebook payload.
5. The candidate must carry an approval record whose approver matches the trusted key principal.
6. The candidate must name the SHA-256 hash of the current active payload as its parent and have a strictly greater MAJOR.MINOR.PATCH version.
7. Only after all checks pass may a separately controlled activation process consider publishing it.

The root fingerprint MUST NOT be read from the same untrusted directory as the registry. Do not commit a real production root private key, maintainer private key, or production root fingerprint to this repository.

## Commands

```sh
cargo run -- rulebook verify-registry signed-registry.json <64-hex-root-fingerprint>
cargo run -- rulebook compare active-payload.json candidate-payload.json
cargo run -- rulebook verify-update active-payload.json candidate-envelope.json signed-registry.json <64-hex-root-fingerprint>
```

The low-level `verify-signed` command remains available for testing and should only be used with a registry already verified by `verify-registry`. Production update processing should use `verify-update`.

## Update Center lifecycle

`DISCOVER → FETCH → VERIFY SOURCE → CLASSIFY → COMPARE → IMPACT REVIEW → HUMAN APPROVAL → SIGN → VERIFY TRUST CHAIN → TEST → ACTIVATE → AUDIT`

This phase implements the cryptographic trust-chain checks and a basic JSON top-level comparison command. It does not yet implement web source discovery, standards authenticity checks, full semantic impact mapping, a graphical UI, signing ceremony, live activation, durable audit-log storage, or rollback orchestration.

## Rollback and history

Rollback must never erase or rewrite the previous approved record. It must be represented as a new, human-approved and signed Rulebook version whose payload explicitly references the version/hash being restored. The update verifier's parent-hash rule preserves a linear chain from the currently active payload.

## Security limitations

A pinned fingerprint is only as trustworthy as the deployment mechanism that supplies it. If an attacker controls both the executable/deployment configuration and the pin, they can replace the trust anchor. Production deployment therefore requires protected configuration, restricted host administration, backup/recovery and independent review. Ed25519 proves possession of a signing key; it does not prove that the person is legally authorized, that cited standards are authentic, or that a policy is scientifically correct.

No real key is generated or stored by this repository. The example signed registry is deliberately nonfunctional and must never be trusted.
