# H0.2.7 — Control Evidence Binding

**Status:** Implemented on the H0.2.7 development branch; pending review and CI.
**Parent:** H0.2.6 Rulebook Enforcement Core.

## Objective

Close the H0.2.6 gap where a signed approved rule only had to contain non-empty control IDs. H0.2.7 requires each control ID used by a subsystem gate to resolve to a control-evidence record inside the same signed Rulebook payload.

## Required control record

Each record contains:
- stable `control_id` and exactly one governed `gate`;
- implementation state (`planned`, `implemented`, `retired`, `blocked`);
- verification state (`pending`, `verified`, `failed`, `expired`);
- accountable owner and explicit scope;
- UTC verification timestamp;
- at least one test ID and one evidence ID.

A gate is denied unless every control referenced by every approved in-scope rule resolves to a record marked `implemented` and `verified`, with non-empty owner/scope/timestamp/test/evidence references and matching gate.

## CLI integration

The H0.2.7 gate preflight checks the control-evidence catalogue after cryptographic authorization. Missing catalogue, unresolved IDs, stale/unverified state labels, incomplete evidence references and gate mismatch fail closed.

## Evidence semantics and limits

The signed record proves only that the authority-approved payload declares a control and references tests/evidence. It does not prove that a test actually ran, that an artifact hash corresponds to the claimed artifact, or that a production binary invokes the gate. A future evidence collector must verify CI run identities, artifact digests, deployment attestations and expiry/revocation policy. Real subsystem integrations remain pending until those modules exist and have integration tests.

No production key, personal identity, threshold, certification or external standards-conformity claim is introduced by this phase.
