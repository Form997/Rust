# H0.2.10.1 — Cross-System Rulebook Control Matrix

**Status:** Design baseline; proposed controls, not a claim of completed integration.
**Parent:** H0.2.9 branch `h0-2-9-trusted-attestation-audit-anchor`.
**Working branch:** `h0-2-10-1-cross-system-control-matrix`.
**Merge policy:** No merge to `main` or any parent branch without explicit owner approval.

## 1. Purpose and completion boundary

This milestone defines a single, reviewable control map for every AL subsystem that can create, transform, train on, validate, package, publish or execute project artifacts.

It does **not** yet wire enforcement into every subsystem. It establishes:
- the subsystem inventory and trust boundaries;
- the minimum Rulebook decision required at each boundary;
- the evidence expected from each gate;
- fail-closed conditions and explicit exceptions;
- acceptance criteria for the later implementation milestones.

H0.2.10.1 is complete when this matrix is reviewed and accepted as the implementation contract. H0.2.10.2 onward may then implement the shared gate and integrations independently.

## 2. Governing invariants

1. The approved, validly signed Rulebook bundle is the policy authority. A draft, unsigned, revoked, expired, malformed or tampered bundle is not an approved policy.
2. The owner-designated human authority alone may approve, sign and publish official Rulebook changes. AI, CI, maintainers and subsystem owners may propose or evaluate changes but cannot silently approve policy.
3. Each decision is scoped to a named operation, artifact, subsystem, Rulebook version and evaluation time.
4. A control marked mandatory cannot be bypassed by a lower-level subsystem setting.
5. Missing required evidence, invalid signatures, unresolved policy conflicts, stale trust data or unverifiable provenance produce DENY or REVIEW according to the policy's explicit disposition. They never become implicit ALLOW.
6. An ALLOW is not a general endorsement of an artifact. It means only that the declared controls for the requested operation passed under the recorded policy snapshot.
7. Legal obligations and applicable regulations take precedence over voluntary project policy. Conflicts must be surfaced and recorded, not hidden by automated interpretation.
8. Every gate decision must be auditable and reproducible from its input references, policy digest, verifier version and evidence references.

## 3. Shared decision contract

All subsystem gates must converge on the following logical result:

| Field | Requirement |
|---|---|
| decision_id | Unique identifier for this evaluation |
| decision | `ALLOW`, `DENY` or `REVIEW` |
| operation | Exact operation requested (for example compile, execute, train, publish) |
| subsystem | Stable subsystem identifier |
| subject | Artifact type and immutable digest where available |
| rulebook_version | Exact approved bundle version |
| rulebook_digest | Digest of the verified policy bundle |
| evaluated_at | UTC timestamp |
| verifier | Gate implementation name and version |
| controls | Evaluated control IDs and outcomes |
| evidence_refs | Immutable evidence/artifact references and digests |
| reasons | Machine-readable reason codes plus human-readable explanation |
| audit_ref | Append-only audit event reference, when the audit service is available |

No subsystem may reinterpret `REVIEW` as `ALLOW`. An unavailable gate is not a successful gate.

## 4. Cross-system control matrix

The control IDs below are stable design identifiers for this milestone. They must be mapped to the authoritative control catalogue before being treated as approved controls.

| Subsystem | Boundary / operation | Minimum Rulebook checks | Required evidence | Failure disposition |
|---|---|---|---|---|
| AL source / parser / compiler | Parse, type-check, compile | Language version, grammar contract, safety rules, compiler compatibility, prohibited constructs | Source digest, compiler version, diagnostics, control results | DENY invalid or prohibited source; REVIEW unresolved compatibility |
| AL package / dependency resolver | Resolve and package dependencies | Approved source/licence status, integrity, version constraints, vulnerability policy | Lockfile, package digests, provenance/licence records, scan result | DENY integrity/licence failure; REVIEW unknown provenance |
| AL runtime / execution engine | Load and execute program | Runtime policy, capability grants, sandbox profile, operation permissions | Program digest, runtime build, capability manifest, sandbox decision, execution audit | DENY absent capability or failed sandbox; REVIEW unknown policy |
| AI inference / assistant | Generate, explain or transform AL | Model-use policy, data boundary, safety constraints, output validation requirements | Model/version identity, prompt/task classification where permitted, output digest, validator result | Untrusted output; DENY execution until validated; REVIEW policy ambiguity |
| Dataset ingestion / preparation | Import, clean, transform or export data | Provenance, licence, consent/privacy basis, allowed purpose, retention and minimization | Dataset manifest, source records, licence evidence, transformation lineage, privacy review | DENY prohibited/unlicensed use; REVIEW uncertain rights or basis |
| Training / fine-tuning / evaluation | Train, tune, select or evaluate model | Approved dataset set, training protocol, metric definitions and thresholds, compute/safety constraints | Run manifest, dataset digests, code/config digests, metric cards, logs, evaluation report | DENY unapproved inputs or failed mandatory metrics; REVIEW unset thresholds |
| Scientific / agronomy modules | Calculate, simulate or publish scientific outputs | Domain assumptions, units, model version, validation protocol, uncertainty and evidence requirements | Formula/model version, input provenance, units, test datasets, validation and uncertainty report | DENY dimensional/validation failure; REVIEW unsupported assumptions |
| Build / CI / release | Build binaries, images or installers; release | Signed policy, required tests, dependency integrity, artifact provenance, release controls | Commit SHA, workflow/job identity, test results, artifact digest, attestation | DENY failed or unverifiable release gate |
| Rulebook Update Center | Discover, stage, approve, publish or rollback policy | Source classification, applicability, impact assessment, owner approval, signature, version and rollback integrity | Source snapshots/URLs, diffs, impact report, approval record, signature, audit chain | DENY unauthorized publication; REVIEW disputed or unverified source |
| Audit / evidence / trust services | Record, verify or consume evidence | Signature, digest, expiry, revocation, chain continuity, trust-root validity | Signed envelopes, evidence manifests, audit records, external attestations | DENY tampering/revocation; REVIEW unavailable or stale trust anchor |

### 4.1 Evidence strength labels

Evidence must be described without overstating what it proves:

- **E0 — Assertion:** a record says a control passed; no independent verification.
- **E1 — Reproducible local check:** command, inputs and output are retained sufficiently to repeat the check.
- **E2 — CI-bound evidence:** run/job identity, repository and commit are checked against the configured CI provider metadata.
- **E3 — Cryptographically attested artifact:** artifact digest and signer/workflow identity are verified under a declared external trust model.
- **E4 — Independent review/witness:** evidence has been checked by a separately governed party or trust domain.

These are descriptive levels, not universal quality scores. A higher label does not prove scientific truth, lawful licensing or human policy approval. Each control must state the minimum evidence level it requires; unspecified levels remain **NOT SET** until approved.

## 5. Control catalogue mapping

Before implementation, each matrix row must map to one or more control records in the existing governance control catalogue. Each mapped control must declare:
- stable control ID and version;
- owner and subsystem scope;
- mandatory / conditional / advisory classification;
- applicable operation and jurisdiction where relevant;
- verification method and pass/fail semantics;
- evidence type and minimum evidence strength;
- policy source and source classification;
- effective date, expiry/review date and revocation handling;
- failure disposition;
- implementation status and verification status.

A control with no approved threshold, no testable verification method or unresolved applicability must be marked `NOT_SET` or `REVIEW_REQUIRED`; no numerical threshold may be invented to fill a gap.

## 6. Gate placement and precedence

The shared gate is a policy decision service, not a replacement for local validation.

1. **Pre-operation gate:** checks permission and required policy before expensive or irreversible actions (execution, training, publication, release).
2. **In-operation safeguards:** runtime sandbox, capability enforcement, data minimization and resource limits remain enforced locally.
3. **Post-operation evidence:** outputs, test results and audit references are bound to the decision record.
4. **Release gate:** independently rechecks the complete required evidence set against the exact release candidate digest.

Local safety checks may be stricter than the shared gate. They may not weaken mandatory central controls. If the central verifier is unavailable, operations classified as mandatory-gated must fail closed; explicitly designated read-only or emergency-safe functions may continue only if the approved Rulebook defines that exception.

## 7. Minimum acceptance criteria for H0.2.10.1

- [ ] Every known AL subsystem is listed or explicitly marked out of scope with rationale.
- [ ] Every listed subsystem has a named boundary and operation.
- [ ] Mandatory checks, evidence and failure dispositions are defined.
- [ ] Shared decision contract is consistent across rows.
- [ ] Evidence strength labels are documented with limitations.
- [ ] Every proposed control ID is mapped to the authoritative catalogue or marked pending.
- [ ] Unknown thresholds and unverified standards remain NOT SET.
- [ ] Owner review confirms that this document is an implementation contract, not an assertion that gates are already integrated.
- [ ] Follow-on H0.2.10.2 can implement the common gate without changing subsystem-specific policy semantics.

## 8. Test plan for subsequent implementation

The shared gate and each adapter must eventually demonstrate at least:
1. valid approved bundle + complete evidence → ALLOW;
2. invalid signature or altered bundle → DENY;
3. revoked/expired evidence → DENY;
4. missing mandatory evidence → DENY or REVIEW as specified, never ALLOW;
5. unknown mandatory threshold → REVIEW / blocked training or release;
6. wrong subsystem, operation or subject digest → DENY;
7. gate service unavailable → fail-closed for mandatory-gated operations;
8. valid local checks cannot override a central DENY;
9. audit record binds decision, policy digest, subject digest and evidence references;
10. replay of an old decision for a different artifact or operation is rejected.

These are future acceptance tests; they are not claimed as already implemented or passed in H0.2.10.1.

## 9. Explicit exclusions

This milestone does not:
- integrate or enforce gates in compiler, runtime, AI, training, scientific modules or release pipelines;
- define numerical scientific or model-quality thresholds;
- certify compliance with international standards or Vietnamese law;
- prove source licensing, dataset consent or scientific correctness by schema validation alone;
- establish a production identity system, HSM, independent signing service or immutable external audit archive;
- authorize merge of H0.2.9 or any stacked branch into `main`.

## 10. H0.2.10 sequence

- **H0.2.10.1 — Control matrix:** this document; establishes the integration contract.
- **H0.2.10.2 — Shared Rulebook gate API:** typed decision model, policy snapshot loading, fail-closed semantics and unit tests.
- **H0.2.10.3 — Build and release adapter:** block build/release on failed mandatory controls and bind evidence to exact artifacts.
- **H0.2.10.4 — Data and training adapter:** enforce dataset/run manifests, metric cards and approval state.
- **H0.2.10.5 — Remaining subsystem adapters and end-to-end verification:** runtime, AI and scientific modules, with an integration report and explicit residual-risk register.

Each sub-milestone must be independently reviewable and stoppable. A completed sub-milestone does not imply completion of the next one.
