# H0.2.10.3 — Build & Release Gate Adapter

**Status:** Implementation candidate; CI validation required.
**Parent:** `h0-2-10-2-shared-rulebook-gate-api`.
**Working branch:** `h0-2-10-3-build-release-gate-adapter`.
**Merge policy:** No merge to parent or `main` without explicit owner approval.

## Purpose

Connect the shared Rulebook Gate API to a concrete artifact authorization boundary. The adapter reads the exact artifact bytes, computes SHA-256 itself, and submits a request to the `release` subsystem gate. It never trusts a caller-supplied artifact digest. The `build` operation here means authorization of a produced build artifact (post-build); it does not prevent a compiler process from starting or gate every internal build step.

## CLI

```sh
al rulebook release-gate <build|package|publish_release> <artifact-file> <evaluated-at-utc> <decision-id> <verifier-version> <evidence-refs.json> <signed-envelope.json> <signed-registry.json> <pinned-root-fingerprint-hex>
```

The evidence references file is a JSON array of strings. The root fingerprint must be supplied by separately protected deployment configuration. The command prints a structured decision and exits successfully only for `ALLOW`; DENY, REVIEW, malformed input, unreadable artifacts and trust failures exit non-zero.

## Security behavior

- The subject digest is computed from the bytes actually read by the adapter.
- Only the three explicitly named release operations are accepted.
- The shared gate verifies the trusted registry, owner-signed approved Rulebook, operation-scoped rule and evidence references.
- An ALLOW is scoped to one operation and one exact artifact digest; it is not blanket authorization.
- The adapter does not publish, deploy, sign or execute the artifact.
- Callers must not treat a printed ALLOW as durable authorization until decision/audit persistence is transactionally enforced by a later integration.

## CI coverage and limits

CI compiles/tests the adapter, checks SHA-256 test vectors and exact-byte binding, and smoke-tests fail-closed behavior for untrusted authority, unsupported operations and missing artifacts. These negative tests prove rejection paths, not a positive production authorization path. Positive authorization still requires a valid owner-signed Rulebook and independently provisioned root trust material; no production keys are stored in the repository.

This adapter currently covers the release boundary only. It does not yet intercept every build tool, package manager, deployment platform or external release channel. It is not a substitute for protected GitHub environments, branch rules, artifact attestations or human release approval.


## R01–R06 closure work (in progress)

This section records implementation evidence and the remaining boundaries. A passing unit test is not a production deployment attestation.

### R01 — Positive and negative trusted-authority paths

- Added deterministic test-only Ed25519 root and owner keys; no private key or production trust material is stored as a fixture.
- Positive path verifies the out-of-band root fingerprint, root-signed trust registry, active owner key, owner-signed approved Rulebook, release operation scope, control evidence and exact artifact digest, then obtains an artifact-scoped ALLOW.
- Negative tests cover wrong root pin, revoked owner key, tampered signed Rulebook and missing evidence (REVIEW).
- These tests prove the verifier's local cryptographic and policy path, not production key provisioning or identity ceremony.

### R02 — Preflight and postflight build boundary

- Added `run_guarded_build`: hashes the exact build-plan bytes and requires a release/build ALLOW before invoking the supplied build callback; after the callback, it hashes and evaluates the produced artifact again.
- Tests prove that a revoked signer prevents the callback from running and that a valid test authority passes both sides.
- This is an application-level API contract. It cannot stop direct invocation of external build tools or bypasses outside the process. Production enforcement still requires OS/CI permissions, protected runners and making this orchestrator the only permitted build entry point.

### R03 — Durable audit before authorization is returned

- Audit append now writes the record in one append operation and calls `sync_all` before reporting success.
- Added `release-gate-audited` and `evaluate_release_artifact_audited`; the decision is appended and the complete chain re-verified before the caller receives it. Audit failure returns an error and does not return ALLOW.
- Tests cover successful audited ALLOW and audit destination failure.
- `sync_all` requests filesystem durability; it does not prove remote replication, immutable/WORM retention, crash behavior on every filesystem, or atomicity across concurrent writers. Production must use a single-writer/locking policy and an independently retained anchor or append-only service before irreversible release actions.

### R04 — Release route inventory and bypass coverage

- Added a JSON Schema, a `NOT_SET` inventory fixture, a Rust assessment function and `release-routes-verify` CLI.
- Missing/unverified inventory produces REVIEW; a route that does not require the gate is DENY.
- Even a structurally complete inventory remains REVIEW because independent completeness attestation is not implemented.
- The actual external release channels, package registries, deployment platforms and bypass paths have not been inventoried in this repository. This is deliberately NOT_SET; no claim of universal route coverage is made.

### R05 — Trust key lifecycle

- Added a root-rotation test proving a new root requires a new out-of-band fingerprint pin; existing tests also cover revoked owner keys, invalid root pins and tampered registries.
- Production key ceremony, HSM/KMS custody, dual control, recovery, emergency revocation, trusted identity proofing and operator runbooks remain NOT SET.
- Test keys are deterministic test-only material and must never be reused in production.

### R06 — End-to-end integration evidence

- Added a combined test covering signed authority verification, build-plan preflight, guarded build callback, artifact postflight, audited release decision and audit-chain verification.
- This is an in-process integration test using test-only keys and temporary files. It is not a live deployment, external release-channel interception test or independent security assessment.

### Current closure status

R01, R02, R03, R05 and R06 have implementation/test coverage in the repository, subject to the explicit limits above. R04 is intentionally incomplete because the real-world release-route inventory and independent completeness evidence are not available. Therefore **H0.2.10.3 remains OPEN / NOT READY FOR PRODUCTION** until R04 is completed with owner-supplied route inventory, all six CI checks pass on the final head, and production deployment controls are independently verified. No merge is authorized.
