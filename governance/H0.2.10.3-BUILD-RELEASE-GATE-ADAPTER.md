# H0.2.10.3 — Build & Release Gate Adapter

**Status:** Implementation candidate; CI validation required.
**Parent:** `h0-2-10-2-shared-rulebook-gate-api`.
**Working branch:** `h0-2-10-3-build-release-gate-adapter`.
**Merge policy:** No merge to parent or `main` without explicit owner approval.

## Purpose

Connect the shared Rulebook Gate API to a concrete artifact authorization boundary. The adapter reads the exact artifact bytes, computes SHA-256 itself, and submits a request to the `release` subsystem gate. It never trusts a caller-supplied artifact digest. The `build` operation here means authorization of a produced build artifact (post-build); it does not prevent a compiler process from starting or gate every internal build step.

## CLI

```sh
al rulebook release-gate <build|package|publish_release> <artifact-file> <evaluated-at-utc> <decision-id> <verifier-version> <evidence-refs.json> <signed-envelope.json> <signed-registry.json> <pinned-root-fingerprint-hex>
```

The evidence references file is a JSON array of strings. The root fingerprint must be supplied by separately protected deployment configuration. The command prints a structured decision and exits successfully only for `ALLOW`; DENY, REVIEW, malformed input, unreadable artifacts and trust failures exit non-zero.

## Security behavior

- The subject digest is computed from the bytes actually read by the adapter.
- Only the three explicitly named release operations are accepted.
- The shared gate verifies the trusted registry, owner-signed approved Rulebook, operation-scoped rule and evidence references.
- An ALLOW is scoped to one operation and one exact artifact digest; it is not blanket authorization.
- The adapter does not publish, deploy, sign or execute the artifact.
- Callers must not treat a printed ALLOW as durable authorization until decision/audit persistence is transactionally enforced by a later integration.

## CI coverage and limits

CI compiles/tests the adapter, checks SHA-256 test vectors and exact-byte binding, and smoke-tests fail-closed behavior for untrusted authority, unsupported operations and missing artifacts. These negative tests prove rejection paths, not a positive production authorization path. Positive authorization still requires a valid owner-signed Rulebook and independently provisioned root trust material; no production keys are stored in the repository.

This adapter currently covers the release boundary only. It does not yet intercept every build tool, package manager, deployment platform or external release channel. It is not a substitute for protected GitHub environments, branch rules, artifact attestations or human release approval.
