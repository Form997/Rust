# H0.2.4 — Core Rulebook Authority Gate

**Status:** Proposed implementation pending independent review and deployment hardening.  
**Branch:** `h0-2-4-core-rulebook-authority`

## Purpose

H0.2.4 adds a cryptographic verification gate for signed Rulebook bundles. A proposed change is not an active policy. The verifier accepts only an approved payload signed by a currently active trusted Ed25519 key with the `rulebook_authority` role, and the approval identity must match that key's principal.

## CLI

```sh
cargo run -- rulebook verify-signed envelope.json trusted-keys.json
```

Exit code 0 means the signature and approval metadata verify against the supplied trust registry. Exit code 1 means verification failed. This command verifies authority; it does not itself install, activate, or distribute the bundle.

## Cryptographic contract

- Algorithm: Ed25519.
- Signed message: compact UTF-8 JSON serialization of `payload` using serde_json's default lexicographically key-sorted object representation; array order is preserved.
- Envelope fields: `algorithm`, `key_id`, `payload`, `signature_base64`.
- Trusted key fields: `key_id`, `principal_id`, `role`, `status`, `public_key_base64`.
- Payload must declare `status=approved`; approval must declare `state=approved`, a non-empty approver matching the trusted key's principal, and a timestamp.
- Revoked, unknown, malformed, wrong-role, mismatched-identity, modified-payload and invalid-signature cases are rejected.

## Human authority and private-key custody

The Rust code contains verification only. It does not generate, store, export or request private signing keys. The private key must remain under the direct control of the designated human authority, preferably in a hardware-backed or otherwise independently protected signing environment. AI and ordinary development accounts must never receive it.

## Critical root-of-trust limitation

The verifier trusts the public-key registry supplied to it. If an attacker can replace both the envelope and that registry, they can nominate a new key. Therefore the production registry MUST be anchored outside the mutable project checkout (for example, a protected deployment configuration or separately controlled root-of-trust), with changes requiring approval by the currently trusted authority. The example registry in this repository is deliberately empty and is not a production trust store.

This phase does not yet implement a secure key ceremony, hardware security module integration, multi-person recovery, key rotation ceremony, signed registry updates, bundle activation/rollback, operating-system account enforcement, or repository branch protection. Do not claim that “only one person can change policy” is fully enforced in production until these controls are independently implemented and tested.

## Tests

Unit tests generate a deterministic test key in memory and verify:
- valid signature accepted;
- payload tampering rejected;
- unknown key rejected;
- revoked key rejected;
- approval identity mismatch rejected;
- non-approved payload rejected.

The test key is ephemeral test data, not a production authority key.
