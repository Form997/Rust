# H0.2.10.2 — Shared Rulebook Gate API

**Status:** Implementation candidate; awaiting CI and owner/security review.
**Parent:** H0.2.10.1 branch `h0-2-10-1-cross-system-control-matrix`.
**Working branch:** `h0-2-10-2-shared-rulebook-gate-api`.
**Merge policy:** No merge to parent or `main` without explicit owner approval.

## 1. Purpose

Provide one typed decision contract for AL subsystem adapters. Each evaluation binds a decision to one subsystem, operation, exact subject digest, signed Rulebook snapshot, verifier version and evidence references.

The API returns exactly one of:
- `ALLOW`: all checks implemented by this API passed for this request only;
- `DENY`: a policy, signature, scope or operation check failed;
- `REVIEW`: required control evidence or evidence references are incomplete or unresolved.

Neither REVIEW nor an unavailable API may be interpreted as ALLOW.

## 2. Implementation

- `src/shared_gate.rs`: request/decision types, root-verified registry wrapper, operation allowlists, signed Rulebook verification, operation-specific policy matching, control-evidence binding, policy digest and fail-closed decisions.
- `src/main.rs`: CLI command `rulebook gate-evaluate`.
- Existing `authority.rs`, `policy_gate.rs` and `control_evidence.rs` remain the underlying trust and control verification components.

### Trust boundary

The public evaluation API accepts `VerifiedRegistry`, not arbitrary registry JSON. Its constructor verifies the signed registry using an out-of-band pinned root fingerprint. The caller must obtain that fingerprint from separately protected deployment configuration; it must not be read from the same untrusted repository checkout as the registry.

The Rulebook envelope is then checked against that verified registry. A signed payload must carry approved status, approved human approval, matching trusted signer principal and a valid Ed25519 signature.

## 3. Request contract

A `GateRequest` contains:
- `decision_id`: caller-generated stable identifier;
- `subsystem`: currently supported gate identifier;
- `operation`: exact operation name, checked against the subsystem allowlist and an approved Rulebook rule's `operations` array;
- `subject_type` and `subject_sha256`: exact artifact identity;
- `evaluated_at`: RFC3339 UTC timestamp ending in Z, supplied by the trusted caller;
- `verifier_version`: version of the gate implementation;
- `evidence_refs`: non-empty references that must resolve in the signed control-evidence catalogue.

The API rejects malformed identifiers, non-lowercase/non-64-character SHA-256 digests, malformed UTC timestamp shapes and unknown subsystem names. Full calendar/time-source validation remains the responsibility of the trusted caller's clock layer.

## 4. Decision binding

An ALLOW includes:
- decision ID and operation;
- subsystem and subject type/digest;
- exact Rulebook version and SHA-256 digest;
- evaluation timestamp and verifier version;
- resolved control IDs and evidence references.

The Rulebook digest currently hashes compact `serde_json` serialization. This is a provisional serialization contract, not a formally adopted canonical JSON standard. A future format-versioned canonicalization specification and cross-language test vectors are required before long-term interoperability claims.

## 5. Fail-closed behavior

- Invalid signer, signature, approval identity or Rulebook status: DENY.
- No approved rule for the subsystem: DENY.
- No approved rule explicitly naming the requested operation: DENY.
- Operation not in the subsystem allowlist: DENY.
- Missing/unverified control evidence or unresolved evidence references: REVIEW.
- Empty evidence reference list: REVIEW.
- Malformed request: API error; callers must treat it as non-ALLOW.
- Unsupported subsystem: API error; callers must treat it as non-ALLOW.

No branch of this API silently converts missing policy or missing evidence to ALLOW.

## 6. Currently supported subsystem gates

The API currently reuses the seven existing gate identifiers:
`compiler`, `runtime`, `ai`, `training`, `evaluation`, `scientific`, and `release`.

The H0.2.10.1 matrix also names package/dependency, dataset pipeline, Rulebook Update Center and audit/trust services. Those are not yet first-class Gate enum values or integrated adapters. They remain explicit follow-on work; this milestone does not claim all ten matrix rows are wired.

## 7. CLI

```sh
al rulebook gate-evaluate <subsystem> <operation> <subject-type> <subject-sha256> <evaluated-at-utc> <decision-id> <verifier-version> <evidence-refs.json> <signed-envelope.json> <signed-registry.json> <pinned-root-fingerprint-hex>
```

The evidence references file must be a JSON array of strings. The command prints a structured JSON decision. It exits successfully only for ALLOW; DENY, REVIEW, malformed requests and trust failures exit non-zero.

Example operation names:
- compiler: `parse`, `type_check`, `compile`;
- runtime: `load`, `execute`;
- AI: `infer`, `generate`, `explain`, `transform`;
- training: `prepare_training`, `train`, `fine_tune`;
- evaluation: `evaluate`, `benchmark`;
- scientific: `calculate`, `simulate`, `publish_result`;
- release: `build`, `package`, `publish_release`.

## 8. Test scope

Unit tests cover request shape, digest formatting, UTC timestamp shape, subsystem/operation compatibility and unknown gate rejection. Existing authority and policy-gate tests cover signature, signer identity, approval state, scope and control evidence.

CI must run the full Rust test suite and CLI smoke tests after this change. A passing unit suite does not prove production identity isolation, trusted clock integrity, persistent audit delivery, or actual integration at every subsystem boundary.

## 9. Explicit limitations

- No production deployment or live adapter integration is claimed.
- No trusted clock service is implemented in this milestone.
- Decision persistence/audit append is not yet transactionally coupled to returning ALLOW; production callers must not perform irreversible work until the decision is durably recorded and the audit requirement is satisfied.
- No revocation freshness service or online trust-registry refresh is added here.
- No HSM or independently governed signing service is claimed.
- The current evidence catalogue binds evidence IDs and metadata; it does not independently fetch and re-hash each referenced evidence artifact at evaluation time.
- Seven gate identifiers are supported; remaining matrix subsystems require later adapters.
- The API does not define scientific or model-quality thresholds. Unset thresholds remain NOT_SET and must block any operation whose approved policy makes them mandatory.

## 10. Acceptance criteria

- [ ] A request is bound to subsystem, operation and subject digest.
- [ ] Registry trust requires out-of-band root pin verification.
- [ ] Rulebook signature and owner approval are verified before policy use.
- [ ] Operation-specific approved rule is required.
- [ ] Mandatory control evidence is resolved and verified.
- [ ] Missing or malformed inputs never produce ALLOW.
- [ ] Decision output carries policy version/digest, verifier version and evidence references.
- [ ] Full CI passes on the final commit.
- [ ] Owner/security review accepts the API contract and documented limitations.
